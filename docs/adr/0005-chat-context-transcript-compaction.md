# 对话上下文 = 可重放的 transcript + 预算压缩

旧对话把 `chat_messages` 里的文本历史取 `[-16:]` 直接回灌模型，单条工具结果超过 6000 字符截断（`agents/chat_agent.py`）。卡片、工具调用和真实上下文都不落库，无法解释模型"为什么这么说"，也无法在多步任务里稳定复用早期确认过的 id。

## Decision

**持久化层 append-only，模型上下文每次重建。**

- `chat_entries` 是会话的唯一真相源，按 `seq` 追加：用户消息、助手消息、工具调用、工具结果、调查结论、压缩点。被压缩区间**不删除**，只写 `compacted_into_id`，保留追溯能力。
- 每轮模型调用前现场装配：`system + 最近压缩摘要 + 未被压缩的条目 + 本轮用户消息`。
- **工具结果老化**：最近 2 轮保留全文，更早的替换为写入时生成的确定性摘要（工具名 + 关键字段前 200 字；`list_*` 有定制摘要）。不依赖模型事后总结。
- **显式 token 预算**：system、摘要、条目、工具 schema、输出预留全部计入。占用超过窗口 60% 触发自动压缩；窗口、阈值、保留轮数全部可配置。
- **压缩是一次独立的模型调用**，产出固定四段：已确认事实与 id、已完成操作、未完成待办、用户明确说过的偏好/口径。压缩本身作为步骤展示（可展开摘要全文）。
- 自动压缩失败时降级为硬截断并记录告警，不阻断本轮。
- 手动 `/compact` 与自动压缩共用同一张 `chat_compactions` 表和同一套 schema。
- **不回流模型**：卡片、确认预览、完整 prompt/response、`reasoning_content`。
- `token.delta` 只走 Redis 实时推送，不落 `run_events`；最终文本落一条 `chat.message` 事件和 `chat_entries`。断线重连以最终文本为准，不重放打字过程。
- 子 agent 调查在同 Run 内嵌套，只读工具子集，最多 6 轮、每轮 1 个、深度 1，结论落到 `chat_entries` 和 `chat.investigation` 事件。

## Consequences

- `run_events` 不会因流式输出膨胀，SSE 回放速度可控。
- 摘要可能丢 id，导致后续重复查询；缓解是摘要 schema 强制保留 id 段 + 原文可回溯，但不能保证模型不丢。
- 上下文窗口默认按 32768 估算，需要首次长会话后按 `chat.compaction` 的 `tokens_before` 校准。
- 用户偏好段只收"用户明确说过"的内容，且压缩事件可展开检查，避免一次性指令沉淀为长期规则。

## Rejected

- **滑动窗口 + 截断**：多步任务里早期确认的 id 会被裁掉，模型开始编造或反复查询。
- **每条工具结果都写摘要器**：维护成本高；确定性截断 + `list_*` 定制已覆盖主要体积来源。
- **把卡片和确认预览也回灌模型**：展示结构对模型是噪音，且确认卡包含尚未获授权的动作。
- **持久化 token.delta**：一次回答上千次 commit、事件表暴涨，回放变慢。
